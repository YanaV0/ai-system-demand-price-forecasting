\# ADR-03: Архитектурный стиль сервиса (Модульный монолит vs Микросервисы)



\## Статус

Принято (Accepted)



\## Контекст

Проект — учебный, разрабатывается одним человеком в течение семестра.

Требуется:

\- простота локального запуска (одна команда `docker run`);

\- отсутствие сетевых задержек между модулями;

\- готовность к расширению в ЛР-4…ЛР-8 (обучение модели, drift-мониторинг).



Нагрузка на первом этапе: до 50 RPS в момент пакетного расчёта, в остальное время — почти ноль.



\## Рассмотренные альтернативы



1\. \*\*Модульный монолит в одном Docker-контейнере\*\* — единый артефакт, но внутренняя структура разделена на модули (`api/`, `services/`, `ml/`, `data/`, `repositories/`).

2\. \*\*Микросервисная архитектура\*\* — отдельные сервисы: API Gateway, Inference Service, Feature Service, Queue Worker, каждый в своём контейнере, общение по HTTP/gRPC.

3\. \*\*Событийно-ориентированная архитектура\*\* — Kafka/RabbitMQ для взаимодействия.



\## Решение

Выбран \*\*модульный монолит в едином Docker-контейнере\*\* с чётким разделением

кода на модули и явными контрактами между ними.



\## Обоснование

\- \*\*Простота разработки и отладки.\*\* Один `docker compose up` — и всё работает.

\- \*\*Нет сетевых задержек\*\* между модулями (вызов функции вместо HTTP).

\- \*\*Один разработчик\*\* — микросервисы увеличили бы операционную нагрузку

&#x20; (нужно было бы конфигурировать 4–5 контейнеров, сервис-дискавери, мониторинг).

\- \*\*Нагрузка низкая\*\* — нет причин для независимого масштабирования.

\- \*\*Готовность к эволюции.\*\* Если в будущем потребуется масштабировать

&#x20; инференс на GPU, модуль `app/ml/` можно вынести в отдельный сервис

&#x20; без переписывания остального кода.



\## Последствия

\*\*Преимущества:\*\*

\- быстрый старт проекта;

\- минимум инфраструктуры;

\- простое тестирование и CI/CD;

\- низкий порог входа для нового разработчика.



\*\*Риски и ограничения:\*\*

\- единый контейнер — единая точка отказа;

\- масштабирование возможно только целиком (нельзя масштабировать только инференс);

\- при росте команды и нагрузки придётся выделять модули в отдельные сервисы.



\*\*Условия пересмотра решения:\*\*

\- нагрузка > 500 RPS;

\- появление GPU-требований;

\- разделение команды на 3+ разработчика.
