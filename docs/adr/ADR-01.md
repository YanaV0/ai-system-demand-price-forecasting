\# ADR-01: Выбор режима инференса (Synchronous REST API vs Asynchronous Message Queue)



\## Статус

Принято (Accepted)



\## Контекст

Сервис прогнозирования спроса и цен рассчитывает прогнозы на горизонт 7–30 дней

для всех SKU компании. Расчёты запускаются по расписанию (раз в сутки или раз в неделю)

и не требуют ответа в режиме реального времени. Внешний потребитель — ERP/1С, куда

выгружается готовая витрина прогнозов.



Ограничения:

\- 1 разработчик в команде;

\- срок первой версии — 1 семестр;

\- нет требований к задержке < 1 сек;

\- объём данных — до 100 000 SKU × 30 дней.



\## Рассмотренные альтернативы



1\. \*\*Синхронный REST API (FastAPI)\*\* — клиент отправляет запрос, ждёт ответ.

2\. \*\*Асинхронная очередь (Kafka / RabbitMQ + Celery)\*\* — задание кладётся в очередь, результат забирается отдельно.



\## Решение

Выбран \*\*синхронный REST API (FastAPI)\*\* с запуском по расписанию через

Cron или Airflow. Эндпоинт `POST /api/v1/forecast` принимает список SKU и горизонт,

возвращает готовый прогноз.



\## Обоснование

\- Сценарий пакетный, а не потоковый — синхронного REST достаточно.

\- Проще в разработке, отладке и развёртывании (один контейнер).

\- Не требуется брокер сообщений → меньше инфраструктурных затрат.

\- При росте нагрузки переход на очередь возможен без переписывания логики модели.



\## Последствия

\*\*Преимущества:\*\*

\- быстрый старт проекта;

\- меньше кода и зависимостей;

\- простая интеграция с Cron/Airflow.



\*\*Риски и ограничения:\*\*

\- длинные пакетные расчёты занимают HTTP-соединение → нужен таймаут ≥ 30 мин

  или разбивка на батчи по 1000 SKU;

\- не подходит для real-time запросов (но их в текущем сценарии нет).
