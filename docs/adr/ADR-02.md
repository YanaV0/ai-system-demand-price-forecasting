\# ADR-02: Стратегия хранения и версионирования моделей и артефактов



\## Статус

Принято (Accepted)



\## Контекст

Обученная модель прогнозирования (например, LightGBM/Prophet) и её артефакты

предобработки (scaler, encoder, feature transformer) занимают от единиц

до сотен мегабайт. Их нужно:

\- версионировать вместе с кодом;

\- воспроизводимо загружать в сервис инференса;

\- не раздувать Git-репозиторий.



Ограничения:

\- GitHub ограничивает размер файла 100 МБ, рекомендуемый — до 50 МБ;

\- в Git нельзя эффективно хранить бинарники (плохо сжимаются, раздувают историю).



\## Рассмотренные альтернативы



1\. \*\*Хранить модели прямо в Git\*\* (`models/model.pkl`).

2\. \*\*Хранить только метаданные в Git, а веса — во внешнем хранилище\*\* (S3 MinIO, MLflow Model Registry, DVC + S3).

3\. \*\*Хранить всё в локальной файловой системе\*\* без версионирования.



\## Решение

\- В Git хранятся только \*\*метаданные\*\*: `model\_version`, гиперпараметры, DVC-указатели, конфиги обучения.

\- Бинарные веса и артефакты — в \*\*MLflow Model Registry\*\* (или S3 MinIO для учебного проекта).

\- Для воспроизводимости используем \*\*DVC\*\* (Data Version Control) — он хранит в Git только хэш-указатели.



\## Обоснование

\- Git не предназначен для больших бинарников — это замедляет клонирование и раздувает историю.

\- MLflow даёт версионирование, стадии (`Staging`, `Production`) и аудит — что требуется для продакшена.

\- DVC позволяет связать конкретный коммит с конкретной версией модели.



\## Последствия

\*\*Преимущества:\*\*

\- репозиторий остаётся лёгким;

\- воспроизводимость: любой коммит → конкретная версия модели;

\- готовая инфраструктура для CI/CD (загрузка модели из MLflow при деплое).



\*\*Риски и ограничения:\*\*

\- нужен доступ к S3/MLflow в CI;

\- усложнение локальной разработки (нужно поднять MinIO или MLflow локально);

\- .gitignore обязательно должен исключать `\*.pkl`, `\*.onnx`, `\*.pt`, `\*.h5`.
